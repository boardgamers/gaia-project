# Viewer Performance — Investigation & Findings

> Read this before touching viewer rendering, `store.ts` reactivity, or `SpaceHex`/`SpaceMap`/
> `Sector` again. It records what was actually measured, not guessed, so the same profiling work
> doesn't get redone from scratch in a future session. Last updated: **2026-06-27**.

## Bottom line

The perceived "laggy buttons" (Build a Mine, Trade, Research, browser Back) are **not** caused by
the game engine and **will not** be fixed by switching the engine off the client, by a faster CPU,
or — see the Vue 3 section below — by a framework version bump alone. The cost is almost entirely
**Vue 2 re-rendering the SVG hex map**: deep reactivity walking a large state tree, and (until this
session's fix) ~4,500 duplicate `<defs>` SVG nodes re-created on every map re-render.

## Why the engine was ruled out first

Before touching the viewer, the engine itself was benchmarked in isolation (`engine/bench-perf.ts`,
written, run, then deleted — not committed, the result is what matters):

- `Engine.fromData()` + `generateAvailableCommandsIfNeeded()` for a single move replay: **~3.6 ms**.
- This runs purely in JS, client-side, with no network/server involved — confirmed this is the same
  whether the engine is "client-side" or not. **Client-side execution is not the cause of lag** —
  moving the engine to a server would not remove this cost, and the cost is tiny anyway.

So 100% of the budget for a slow click (measured up to ~148 ms before fixes, see below) was in the
viewer layer: Vue reactivity + DOM/SVG diffing, not in game logic.

## How the profiling was done (reproducible)

Tools: Playwright driving the **pre-installed** headless Chromium
(`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`, `executablePath: '/opt/pw-browsers/chromium-1194/chrome-linux/chrome'`),
Chrome DevTools Protocol `Profiler.enable/setSamplingInterval/start/stop`, self-time aggregated by
`functionName + file:line` from the returned `.profile` (nodes/samples/timeDeltas).

1. **Get a mid-game state to click around in.** `engine/fixtures/Beta-2.json` is a *finished* game
   (`ended: true`, round 6) — useless for profiling action buttons, since none are enabled. A
   mid-game snapshot was generated by replaying prefixes of its `moveHistory` with
   `Engine.fromData()` until a round-1 state came up with Build/Research/etc. available, then
   dumped to JSON. That JSON is **not in the repo** (scratchpad-only, this session); regenerate the
   same way if needed again — it's a few lines of script against `engine/fixtures/Beta-2.json`.
2. **Load the app, paste the state via the debug Load/Export modal** (`Wrapper.vue`'s Load button →
   textarea → OK), wait for `#move-buttons .move-button` to appear.
3. **Path A — cold load+render cost**: start the CDP profiler right before clicking "OK" on the
   Load modal, stop it once the move buttons have rendered + one settle frame. This captures
   `store.commit("receiveData", …)` → Vue reactivity setup → full SVG map render.
4. **Path B — per-click cost**: with the map already rendered, repeatedly click the top-row
   `#move-buttons .move-button` elements in sequence (re-querying the DOM each iteration, no page
   reloads — reload loops were a source of flaky `strict mode violation` Playwright errors because
   multiple "OK" buttons exist on screen at once), timing each click to two `requestAnimationFrame`
   callbacks (`raf2()` helper) so the timing covers the actual re-render, not just the JS handler.
5. Aggregate profiler self-time per function across all clicks combined; also record per-click wall
   time individually to catch the single worst click (Build was consistently the worst).

Gotchas hit and fixed along the way (so they aren't rediscovered):
- The Bash tool's sandbox interfered with binding local ports / backgrounding the headless browser —
  needed `dangerouslyDisableSandbox: true` for these specific local-only, no-side-effect profiling
  runs.
- `pkill <name>` returns nonzero when nothing matches, which aborts a `cmd1 && cmd2` chain — append
  `|| true`.

## Root causes found

1. **Deep Vue 2 reactivity over the whole engine state.** `store.ts`'s `receiveData` mutation did
   `state.data = data` where `data` is the entire `Engine` instance (players, map, all hexes,
   buildings, history…). Vue 2 walks that whole object graph with `defineReactive`/`Dep` to make
   every property reactive — and it's **replaced wholesale** on every move, so the deep observation
   is redone every single time, for an object that is read-only/immutable from the UI's point of
   view (nothing inside it is ever mutated in place by a Vue template/`v-model`).
2. **~4,500 duplicate static SVG `<defs>` nodes.** `SpaceHex.vue` (one instance per hex, ~90 hexes
   on a standard board) used to render its own `<defs>` block of federation-line gradients/lines/arcs
   — ~50 SVG nodes, **identical** content for every hex (only depends on the static planet→color
   table, not on hex-specific data). That's ~4,500 redundant nodes created/diffed by Vue on every
   map re-render, even though only `<use href="#...">` references were actually needed per hex.
3. Minor: a few `console.log` calls sat in hot paths (`store.ts`'s move emitter, `Commands.vue`'s
   `handleCommand`/`subscribe`/`emitButtonCommand`, `self-contained.ts`'s move handler) — cheap
   individually but on the critical path of every click.

Confirmed via the CDP profiles: before the fix, `insertBefore`/`createElementNS`/`setAttribute`/
`setAttributeNS` (raw SVG DOM construction) and Vue's reactivity/`_init`/`_render` internals
(`chunk-vendors...js`, minified names like `Dt`/`Li`/`Yi`/`Ln`/`$i`) dominated self-time — not
anything in the engine or in app-level business logic.

## Fixes applied this session

| # | File | Change |
|---|------|--------|
| 1 | `viewer/src/store.ts` | `import Vue, { markRaw } from "vue"`; `receiveData` now does `state.data = markRaw(data)` — opts the whole engine instance out of Vue's deep-reactivity walk. Safe because nothing mutates `state.data` in place; it's always replaced wholesale. |
| 2 | `viewer/src/components/Game.vue` | `handleData()`: moved the `currentMove`/`newTurn`/`data.moveHistory.pop()` handling to run **before** `this.$store.commit("receiveData", data)` (previously after). Needed because that logic used to rely on Vue reactivity firing on `state.data` mutation timing, which no longer deep-observes after fix #1. |
| 3 | `viewer/src/self-contained.ts`, `viewer/src/components/Commands.vue` | Removed `console.log` calls from hot paths (move emitter handler; `handleCommand`, `subscribe()` callback, `emitButtonCommand()`). |
| 4 | `viewer/src/components/definitions/FederationGradients.vue` (new) | Hoisted the federation gradient/line/arc `<defs>` (per planet color) out of `SpaceHex.vue` into one global component, rendered once in `Definitions.vue`'s top-level `<defs>` instead of once per hex instance. |
| 5 | `viewer/src/components/definitions/Definitions.vue` | Registered and rendered `<FederationGradients />` once, globally. |
| 6 | `viewer/src/components/SpaceHex.vue` | Removed the per-hex duplicated `<defs>` block entirely (now reuses the global one via existing `<use>`/`url(#federation-gradient-...)` references, which already worked by id — no template logic changed, just deleted the duplicate definitions). Removed the now-unused `planetColors` data property and the `planets` default import (kept `planetNames`). |

These are **Tier 1** (#1–3: reactivity + dead weight) and **Tier 2** (#4–6: de-duplicate SVG defs)
from the scoping discussion — the user explicitly chose "Tier 1 + Tier 2" over a larger Tier 3
rework.

## Measured results

Same profiling harness, same mid-game state, before vs. after fixes 1–6:

| Scenario | Before | After | Change |
|---|---|---|---|
| Cold load → full map render (Path A wall clock) | 1185 ms | 993–995 ms | **-16%** |
| "Build a Mine" button click (worst single click, Path B) | 148 ms | 81 ms | **-45%** |
| Median action-button click (Path B, e.g. Pass/Research/Free action) | ~26 ms | ~26 ms | unchanged (these were already cheap; they don't re-render much of the map) |

Verified no regressions: visual screenshots before/after match; full build→move flow exercised
end-to-end with zero new console errors; deployed to the Vercel preview and confirmed green.

Committed as `f1aca63` ("perf(viewer): cut map render cost and skip deep reactivity"), pushed to
`claude/quirky-thompson-gt0n0h`, deployed to Vercel.

## Still open (not done — Tier 3, only if asked for)

- **Build a Mine is still 81 ms**, the single worst click. The remaining cost is the highlight/range
  computation re-rendering `polygonClasses`/`planetClasses`/warnings across all ~90 `SpaceHex`
  instances every time the selection/highlight set changes (each hex component re-evaluates several
  getters that scan `highlightedHexes`, `mapModes`, federations, etc.). Reducing this further means
  either memoizing per-hex highlight state more aggressively or restructuring `SpaceMap`/`SpaceHex`
  to avoid re-touching every hex component when only a subset of hexes actually changed class —
  this is a real component-architecture change, not a one-line fix, which is why it was scoped out
  as Tier 3.
- No further `<defs>`-style duplication audit was done beyond `SpaceHex.vue`'s federation block;
  `Buildings.vue`/`Filters.vue` (also rendered once globally via `Definitions.vue`) were not
  re-audited for the same per-instance-duplication pattern, but a quick check found no second
  instance of it.

## Vue 2 → Vue 3 migration: is it worth it for render speed?

Short answer: **no, not on its own — it would not fix the thing that was actually measured as the
bottleneck.** Don't do this as part of "getting the foundation right" for Lost Fleet; it's a
separate, large, mostly-orthogonal project.

Reasoning, grounded in what this session measured:
- Vue 3's reactivity (`Proxy`-based) is cheaper than Vue 2's `Object.defineProperty` walk **only**
  for the case where you actually let Vue observe a big object. That cost is already eliminated here
  via `markRaw()` (fix #1) — Vue 2.7 (what this app already runs, confirmed in `package.json`) ships
  `markRaw` for exactly this purpose, so the "deep reactivity over a big state tree" problem is
  already solved in Vue 2, not something only Vue 3 can solve.
- The dominant cost in the profiles — confirmed by `insertBefore`/`createElementNS`/`setAttribute`/
  `setAttributeNS` dominating self-time — was **raw SVG DOM node count and diffing**: ~90 `SpaceHex`
  components each rendering many child elements (`<use>`, `<text>`, `Building`/`Planet` subcomponents,
  ships, customs posts, trade tokens), most of it redundant per-hex `<defs>` (now fixed) and
  per-hex highlight recomputation (still open, Tier 3 above). Vue 3's compiler-informed diffing
  (block tree / patch flags) helps with this *only if the components are rewritten with the Vue 3
  compiler's optimizations in mind* (e.g. `<script setup>`, avoiding `v-for` over large lists without
  keys that change, hoisting static vnodes) — a like-for-like Options-API port of the same
  `SpaceHex.vue` template to Vue 3 would see a modest gain at best, not a step-change, because the
  problem is node *count*, not which framework is diffing the nodes.
- Cost side: this app is Vue 2.7 + `vue-class-component`/`vue-property-decorator` (class-based
  components, used throughout `SpaceHex.vue` and friends) + Vuex 3 + `bootstrap-vue` + webpack 4 via
  `vue-cli-service`. Vue 3 migration would require: rewriting every class-component to `defineComponent`
  or `<script setup>` (every `.vue` file in `viewer/src/components`), Vuex 3 → 4 (or Pinia), dropping
  or replacing `bootstrap-vue` (no Vue 3 release of the original package — would mean
  `bootstrap-vue-next` or removing Bootstrap entirely), and likely the build tooling too (vue-cli is
  unmaintained for Vue 3; would push toward Vite). That's a multi-week rewrite touching nearly every
  file in the viewer, for a "modest gain at best" on the one metric (render speed) being optimized.
- If render speed for the hex map specifically becomes the priority again, the higher-leverage next
  step is the Tier 3 item above (reduce per-hex highlight re-render) or restructuring the map to
  render fewer/larger SVG primitives — both deliver more, for less risk, than a framework migration.

**Recommendation: skip the Vue 3 migration.** Treat the current foundation (Vue 2.7 + the Tier 1/2
fixes above) as good enough to build Lost Fleet features on. Revisit Tier 3 only if a specific
interaction is still reported as laggy after Lost Fleet adds more board state to render.
